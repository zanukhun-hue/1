# Схема Supabase

`supabase_schema.sql` объединяет пять таблиц из настроек проекта: `edit_submissions`, `site_visits`, `site_events`, `plugin_reports`, `plugin_requests`, их индексы и публичный бакет `thumbs`. Каталог плагинов остаётся в `plugins.js`.

Открой Supabase → SQL Editor, вставь **весь файл** и нажми Run от имени владельца базы. Схема выполняется в транзакции; повторный запуск сохраняет записи и обновляет перечисленные политики. Существующие таблицы должны иметь столбцы из предоставленной схемы: `CREATE TABLE IF NOT EXISTS` не меняет структуру уже созданной таблицы. Произвольные политики с другими именами файл не удаляет.

Политики соответствуют исходным настройкам статистики: посетители могут добавлять и читать посещения и события. Жалобы и запросы плагинов можно только отправлять со статусом `pending`; их содержимое публично не читается. Видеоработы принимаются на модерацию, публично видны только `approved`.

В присланном SQL правило «Public can read approved edits» разрешало читать также все `pending`: поля пользователя и связи с Supabase Auth в таблице нет. Поэтому доступ ко всем `pending` и публичное изменение заявок убраны. Для восстановления отмены собственной заявки потребуется отдельная проверка владельца. Текущие серверные страницы сайта эту функцию не используют.

Публичность `thumbs` разрешает чтение файлов, но не создаёт разрешений на их загрузку или замену. Уже настроенные политики Storage не меняются.

В Render используются `SUPABASE_URL`, `SUPABASE_ANON_KEY` и серверный `SUPABASE_ADMIN_KEY` (также поддерживается `SUPABASE_SERVICE_ROLE_KEY`). Серверный ключ используется для чтения и закрытия жалоб. При его отсутствии отправка жалобы работает через публичную вставку без запроса приватной записи обратно; уведомление в Telegram приходит без кнопки закрытия этой жалобы. После обновления серверного кода выполни Deploy latest commit в Render. Само выполнение SQL не требует повторного деплоя.

Проверка: `npm run test:schema`. Тест запускает PostgreSQL в памяти через PGlite, повторно применяет схему, воспроизводит старые разрешения, проверяет их исправление и доступ обеих публичных ролей, а также серверный метод отправки жалоб. Проверка не обращается к рабочему Supabase. Бакет моделируется таблицей Storage, `pgcrypto` пропускается, поскольку UUID уже встроены в тестовый PostgreSQL; расширение и Storage API на хостинге этим тестом не проверяются.

Основание для разделения публичной вставки и чтения: [политики RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) и [возврат результата вставки](https://supabase.com/docs/reference/javascript/v1/insert) в документации Supabase.
